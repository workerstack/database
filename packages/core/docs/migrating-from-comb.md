# database — Migrating from comb

[← back to the overview](../../../README.md)

`@workerstack/database` 0.23 shipped comb's names under the new package; 0.24 drops every one of them. The
config shape, the migrations and the generated code work the same; every name changed. This page lists each one,
old to new. Nothing reads the old names, so change all of them at once.

## D1 tracking tables

| comb 0.23                      | @workerstack/database 0.24         |
| ------------------------------ | ---------------------------------- |
| `_comb_migration_hashes`       | `_database_migration_hashes`       |
| `_comb_migration_hash_intents` | `_database_migration_hash_intents` |

A database migrated before 0.24 keeps its history in the old tables, and the new migrator does not read them. Rename
them once per database, before the first deploy on 0.24, outside the migrator (a migration would run against empty
`_database_*` tables and apply every migration again):

```console
$ wrangler d1 execute <db> --remote --command "ALTER TABLE _comb_migration_hashes RENAME TO _database_migration_hashes; ALTER TABLE _comb_migration_hash_intents RENAME TO _database_migration_hash_intents"
$ wrangler d1 execute <db> --remote --command "SELECT name FROM sqlite_master WHERE name LIKE '\_comb\_%' ESCAPE '\'"
```

The second command prints no rows once both are renamed. Run the pair with `--local` for a local database.

## Page cursors

A cursor's key comes from `CURSOR_SECRET` and a label that named the package, and 0.24 changes that label. A cursor
an app handed out on 0.23 or earlier is refused with `invalid_cursor` after the upgrade, as a tampered one is. A
client that gets `invalid_cursor` starts the list again from its first page. Cursors 0.24 mints keep opening.
