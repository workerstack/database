# Query layer

`@workerstack/database/query` is dialect-agnostic: it parses and validates, and produces an AST. `@workerstack/database/query/sqlite` lowers that AST to SQL.

## Filter grammar

PostgREST-style, parsed by `parseFilter()`:

```text
field.op.value          single condition
a.eq.1,b.gt.2           AND at top level
or(a.eq.1,b.eq.2)       OR group
and(...)                nested AND group
status.in.(draft,sent)  list values
@computed.eq.1          computed field (resolved by your resolver)
```

Operators: `eq`, `ne`/`neq`, `gt`, `gte`, `lt`, `lte`, `in`, `nin`, `like`, `ilike`, `is`. `contains`, membership in a JSON array, is no declared type's default: a field spec lists it (see below), and `filterToSQL` runs it on SQLite. `is` takes `null` and `notnull` (any case) on every field, and `true` and `false` on a `boolean` one.

A value that holds `,`, `(`, `)` or `.` is written in double quotes, PostgREST style: `title.eq."Hello, world"`, `title.in.("a,b",c)`; inside quotes `\"` and `\\` escape. Whitespace around a bare value is trimmed.

`like` is case-sensitive and `ilike` ignores ASCII case. In both, `*` is the wildcard and every other character is literal: `like` lowers to SQLite `GLOB` (with `?` and `[` made literal), `ilike` to `LIKE … ESCAPE` (with `%` and `_` escaped). SQLite folds only ASCII case, so `ilike` does not match `Ž` against `ž`; search a pre-normalized column with `q` for that. An empty `in.()` matches nothing and an empty `nin.()` matches everything — neither widens to the whole table.

`validateFilter()` parses and checks in one step, against declared field types, and rejects operators a type does not support — `string` allows `like`, `boolean` allows only `eq`, `ne`, and `is`, and so on — and values that are not of the field's type: a `number` takes a decimal number, a `date` epoch milliseconds, a `boolean` `true` or `false`. A valid result carries each value typed as its field declares. Unknown fields are rejected rather than silently dropped, so a typo returns a 400 instead of the whole table. Unbalanced parentheses, an unclosed `in.(` list and trailing input are syntax errors. Each expression is bounded by `FILTER_LIMITS` — 20 conditions, 3 nested groups, 50 `in`/`nin` values per list, 60 bound values in all, and 50 bytes in a `like` or `ilike` pattern (`maxPatternBytes`: a value with a `*` inside it, measured as SQLite reads it, escaped, so a `[` in a `like` counts as the three bytes of `[[]`) — overridable per call with a third `limits` argument, where a key left out or set to `undefined` keeps its default, a key that is no limit throws a `TypeError` naming it and the limits, and any value but a whole number from 0 throws one naming it, as `createListQuerySchema`'s `limits` do, which hold `maxSortKeys` to 1, and `maxConditions` and `maxSearchTerms` to 1 beside a declared `filter` and `search`. D1 refuses a longer pattern only once it reads a row, so the 400 would depend on the data; the cap refuses it before the query runs. The defaults keep every request the list schema accepts within D1's 100 bound parameters per statement: 60 filter values, 8 search words (`maxSearchTerms`, one `LIKE` each), 10 for a three-key cursor and 2 for limit and offset make 80, which leaves 20 for your `baseWhere`. Raise a limit only on a database without that cap, or with a `baseWhere` that binds less. `createListQuerySchema` also caps the `filter` string at 2048 characters before parsing it (`limits.maxFilterLength`), as it caps `q` at 200, `select` at 500 and `order` at 200. A URL limit counts bytes once percent-encoded (Cloudflare's is 16 KB), and one CJK character is nine of them, so `filter` is also capped at 4608 bytes, `q` at 600, `order` at 200 and `select` at 500 (`REQUEST_BYTES`), each measured as the widest common encoding writes it: a space (`%20` in a URL) and a mark such as `~` or `!` (`%7E`, `%21` in a form) count as 3. With the cursor's 8192, the largest accepted query string is at most 14 KB however a client encodes it, `maxQueryBytes`: 16 KB less 2 KB for the path and the handler's own params. A value holding a lone surrogate, which no URL can carry, is refused. The schema takes any cursor string and `readCursor` answers every one it cannot use, a longer one included, with `invalid_cursor`, so a client restarts on one key; `paginate` carries a sort value too long for the cap by reference (see [Pagination and cursors](#pagination-and-cursors)). `in` and `nin` take a list: `id.in.5` is a 400, not a driver error.

```ts
import { DatabaseError } from "@workerstack/database"
import { validateFilter } from "@workerstack/database/query"

const result = validateFilter("status.eq.published,or(minute_read.lt.5,title.like.intro)", {
	minute_read: "number",
	status: "enum",
	title: "string",
})

/* null when the filter string is empty */
if (result && !result.valid) {
	throw new DatabaseError({ cause: result.errors.join("; "), errorKey: "invalid_filter", status: "bad_request" })
}
const ast = result?.ast
```

A runtime field map, such as one built from a user table's columns, can give a field a spec in place of its type: `{ type, operators?, format? }`. `operators` replaces the type's defaults (`OPERATORS_BY_TYPE`) and may add `contains` on any type, its value typed as one scalar of the type, for an array or multi-select column: `filterToSQL` lowers it as a member of the JSON array the column holds: through `json_each` on SQLite, and on Postgres only on a `json` or `jsonb` column, any other column matching no row. It may also add `in` and `nin` on a `date`, and `gt`, `gte`, `lt` and `lte` on a `string`, which compare text, so stored values must share one form: an ISO instant written in two offsets, `2024-01-01T01:00+01:00` and `2024-01-01T00:00Z`, is one instant that sorts as two. `format: "iso"` on a `date` takes ISO 8601 text, a date (`2024-02-29`) or a date-time with `Z` or an offset (`2024-01-01T00:00+14:00`), naming a real day and time by the proleptic Gregorian calendar (so `0000-02-29` is a day), in place of epoch milliseconds, and types it as the instant it names in `toISOString()`'s form: a bare date is midnight UTC. A fraction past milliseconds is kept: each operator answers the exact comparison, so `lt 00:00:00.9995Z` matches a row stored at `.999` and `eq` matches none, and on a Postgres timestamp, which holds microseconds, the instant compares to the microsecond. A text column that stores `toISOString()` text so compares every spelling of one instant as one, `2024-01-01T01:00+01:00` as `2024-01-01T00:00Z`; on a date or number column `filterToSQL` binds it as the column stores it, epoch milliseconds or a drizzle date in either unit. A spec that lists an operator its type cannot type (`like` on a `number`, `in` on a `boolean`) or puts `format` on no date throws a `TypeError` naming the field, the operator and the type. `parseFilterNumber(raw)` is the number rule on its own: `{ value }`, or `{ error }` for a spelling `Number()` takes and database does not (`0x4d2`, `0b1`, `0o7`, `1e999`) an integer past ±(2^53 − 1), which a double would bind as its neighbour, nonzero digits that read as 0 or a subnormal (`1e-400`, `5e-324`), which would match the rows holding 0, or a decimal a double does not hold as written (`1.000000000000000001`), which would bind as its neighbour.

```ts
import { validateFilter } from "@workerstack/database/query"

const rows = validateFilter("tags.contains.red,due.gte.2024-02-29", {
	due: { format: "iso", type: "date" },
	tags: { operators: ["contains", "is"], type: "string" },
})
```

`parseFilter()` is the parse-only half, returning a `FilterAST` (or `null`) without validating field names.

## Sorting

`parseOrder()` accepts `field.asc`, `field.desc`, and null placement (`field.desc.nullslast`), producing `SortField[]`, or `null` when an entry is empty, names no field (`asc`, `.desc`, a trailing comma) or has whitespace around it (`title.asc, created_at.desc`), or a field is named twice, as `parseFilter()` refuses a filter; the list query schema answers each with an issue on `order` naming it. The published `order` pattern refuses those entries too, but not a field named twice (`title.asc,title.desc`), which only the schema refuses. Computed sorts use the same `@` prefix and are resolved through a `ComputedSortResolver`.

Null placement follows PostgreSQL: nulls sort last ascending and first descending, and an explicit `.nullsfirst` / `.nullslast` always wins. Every SQL builder emits the placement explicitly, so SQLite's opposite default never leaks through. `createListQuerySchema` caps one `order` at 3 keys (`limits.maxSortKeys`).

## Sparse fieldsets

`parseSelect()` implements PostgREST `select`, including relation selection:

```text
select=id,title,author(display_name)
```

`createListQuerySchema({ fields })` is what puts `select` on the wire and `selectable` on `x-database`. A relation's selectable fields are its declared `relationFields`; a relation nested inside one is not selectable, and `select=author(posts(id))` is a 400. Without `fields`, the param is omitted. The query stays fat (sort / id / `_total` / merge keys); the response gets thin. `queryHelpers.paginate` and `queryHelpers.project` honor `parsedFields` as the last mutation of item shape. Do not apply `select=` in the HTTP framework.

`filterBySelect()` cuts a row down to the parsed selection, for call sites outside `queryHelpers.paginate`; `queryHelpers.project` is the one-row wrapper.

`queryHelpers.filterValue(filterAst, field, operator?)` reads the value a filter holds every row's `field` to, and `filterValues(filterAst, fields, operator?)` reads several, so an app can resolve or authorize "the project this list is for" from `project_id.eq.p1`. A value is read only from a condition under the operator asked for (`eq` by default; `ne` and `neq` are one), at the top level of the filter's AND, and the only one there on its field: `project_id.ne.p1`, `project_id.in.(p1,p2)` under `eq`, `or(project_id.eq.p1,project_id.eq.p2)` and `project_id.eq.p1,project_id.eq.p2` read as `undefined`, since the SQL serves rows that value does not name.

## Pagination and cursors

Two modes share one input shape. Offset pagination takes `page` and `limit`; cursor pagination takes `cursor` and `limit`. Responses carry `PaginationResponse`.

A cursor holds the value of **every** sort key, the tiebreak id and the signature of the sort it was minted under (`sortSignature()`), as UTF-8 JSON sealed with XChaCha20-Poly1305: one URL-safe base64 string of a version byte, a random 24-byte nonce, the ciphertext and its tag. A client can read none of the values it carries, a column the endpoint never selects included, and it cannot write one: either would let it learn, request by request, the value of a column it can sort by but not select. `createCursor(row, parsedSort, { cursorScope, cursorSecret })` mints one as `queryHelpers.paginate` does, a long value carried by reference (below) so the cursor stays within the cap `readCursor` holds. The keyset predicate compares all keys lexicographically, each with its own direction and null placement, so a multi-key or nullable order pages without skipping or repeating rows.

Two values seal a cursor. The secret is the app's, at least `MIN_CURSOR_SECRET_BYTES` (32) bytes of UTF-8, and the key is derived from it with HKDF-SHA256. Give every worker the same `CURSOR_SECRET` through its env. The scope names the list: its route and tenant, such as `` `members:${orgId}` ``. It is bound to the seal, so a cursor minted in one list, or for one tenant, opens in no other; without it, a client could mint a cursor where it can write the sort column and replay it where it cannot read that column. Pass both to the builder, `buildListQuery({ cursorScope, cursorSecret, … })`, `buildDerivedListQuery({ cursorScope, cursorSecret, … })`, or `queryHelpers.listOptions(query, { cursorScope, cursorSecret })`, which opens the request's cursor; the query it builds seals the next one, as `queryHelpers.paginate(rows, built)` reads it. A built query holds the secret only in the functions its `pagination` seals and opens with, never as a value, so logging, inspecting or serializing one shows no part of it. `readCursor(cursor, parsedSort, { cursorScope, cursorSecret })` opens a cursor outside a builder. Both are required: a shorter secret or an empty scope is a 500 (`cursor_not_wired`) on the first page. Every builder selects the value its order breaks ties on as `_cursorId`, among its `extras`, and `paginate` mints the next cursor's id from it, so a row's own id, a joined child's beside the parent a derived list orders by, never stands in for it. `createCursor(row, sort, { cursorScope, cursorSecret, idField: "_id" })` mints one by hand from the field a row keys its tiebreak under.

A cursor sealed under another secret or scope, a tampered one, one spelled another way for the same bytes, one minted under another order, and one that does not decode are all `invalid_cursor`, a 400, so rotating the secret ends the lists in flight with a 400. The list schema takes no secret, since schema modules load where no env exists (a gateway's route codegen): it takes the cursor as a string, and only the opening calls read it, so a malformed cursor is `invalid_cursor` as a tampered one is.

A sort value too long for the cap, such as a title a client wrote, goes by reference: the cursor carries the row's id, the longest prefix of the value that fits and the value's length, both in code points, and the keyset reads the value from the row while the row still has that prefix and length. That is exact while the row is there unchanged; an edit that keeps both the prefix and the length still moves the bound to the new value. Once the row is deleted, or edited otherwise, the list resumes from the prefix (followed by U+10FFFF when descending), as a plain cursor resumes where its value stood: it may serve again rows whose value shares that prefix and skips none, under SQLite's binary and NOCASE collations and Postgres's C and POSIX. Under any other Postgres collation neither bound is safe, so the next page of a list whose anchor row was deleted or edited answers `invalid_cursor` (400), and the client starts the list again: `listOptions` adds an `extras` flag that `paginate` reads, so pass its result to `findMany` whole. A reference binds at most what the plain value would in the keyset, so the cursor's share of the parameter budget below holds.

On D1, whose results travel as JSON, a REAL holding ±Infinity reads as null, so a cursor minted from such a row carries null. On a SQLite number key a null cursor value is read back from its row where the row holds ±Infinity, and stays null otherwise. Once that row is deleted the null may have stood for NULL, +Infinity or -Infinity, so the list resumes from the earliest of them in its order (NULL where NULLs come first, else -Infinity ascending and +Infinity descending), which repeats rows and skips none. Set `nonFinite: "exact"` beside `cursorSecret` only when your driver reads ±Infinity back as Infinity, as a local libsql file and bun:sqlite do: a null cursor is then a real NULL, and a deleted NULL anchor resumes right after it. D1, and any driver that returns ±Infinity as null, keep the default.

`readCursor` returns each sort value as the cursor's row read it, a time key as the Date the driver read, an Invalid Date included, a numeric as the text or number its mode reads, and D1's `null` for a REAL ±Infinity as `null`, while the next page binds the value the database stores, which keeps the microseconds of a Postgres time and the fraction of a SQLite timestamp's unit that a Date drops. Bytes come back as a `Uint8Array`, whatever the driver read them as.

For drizzle's relational API, `queryHelpers.listOptions(query, { cursorScope, cursorSecret })` returns `limit`, `offset`, an `orderBy` callback (the sort, its null placement and the id tiebreak) and, on a cursor request, a `where: { RAW }` keyset predicate to AND with your own: `db.query.post.findMany({ limit, offset, orderBy, where })`.

`pagination.count` is the number of rows the filter matches across all pages, or `null` when the response cannot know it. Every builder hands back the columns `paginate` reads as `extras`: the tiebreak (`_cursorId`), an offset page's count (`_total`), and, on a cursor that carries a reference, whether its anchor is gone (`_cursorAnchorGone`); a merged SQLite list, a SQLite derived list with no `anchor`, and an anchored one sorted by an expression with no column, such as `count(*)`, also select the storage class of each sort key and of the tiebreak (`_cursorKeyTypes`), so a key libsql's `intMode: "string"` reads as a decimal string resumes as the integer SQLite stored, never as text, and a REAL ±Infinity, which D1 reads as null, resumes as itself; a Postgres derived list with no `anchor` selects each one's type family there (`float`, `fixed` or `other`), so a `double precision` past 2^53 pages and a `bigint` read as a number is refused. An anchored derived list sorted by a joined table's column does the same for that key, as its anchor row holds no such column: a joined integer past 2^53 is refused rather than resumed from a rounded number. A list sorted by a Postgres `timestamp`, `timestamptz` or `date` also selects the key's stored value as text (`_cursorKeyTexts`), on every list, `listOptions` included: written the same in any session's `DateStyle`, microseconds and `'infinity'` included, so a cursor resumes from the stored value rather than the Date or string the driver read. A Postgres `double precision` or `real` key carries no text, as every text Postgres prints a float in follows the session's `extra_float_digits`: at its default of 1 the driver reads the float exactly, and at 0 or below, which a configuration from before Postgres 12 or a pooler may set, it reads `1.0000000000000002` as `1`, so a page that serves a non-null float key under it is a 500 `sort_not_wired` naming the setting, never a page that skips rows. A Postgres `numeric` read in number mode carries its text the same way, and an expression of `numeric` type or of a type of the database's own that is no float does on a derived list. On SQLite, a seconds-mode timestamp carries its REAL seconds where it is an anchored derived list's joined key or a key of a list with no `anchor`, and on a merged list, which merges by them. A SQLite REAL such a key carries, and a REAL held apart below, goes in the cursor as the text of it SQLite reads back as that REAL, `cast(k as text)` where that reads back and `printf('%!.17g', k)` where it does not, and the next page binds `cast(? as real)`: one SQLite parse of one text, the one the list checked, where D1 parses a bound number's shortest text as another REAL for some values, which skipped rows. A REAL neither text reads back as, as D1 prints some, is a 500 `sort_not_wired` on the page that serves it, naming the key. A non-STRICT SQLite table lets any column hold any storage class, and each drizzle mode reads back as stored only its own: a number mode and a timestamp integers and REALs, a `numeric()` integers and finite REALs, a text TEXT, a buffer or bigint blob BLOBs, a boolean 0 and 1. A list that reads a SQLite key back from its anchor row, `listOptions` included, and a merged list, which merges by it, select the value of any other class such a key holds, its class beside it (`_cursorTextKeys`), so a cursor resumes from the stored value, a `timestamp`'s TEXT, which SQLite orders after every number, among them; a list that binds the key as read answers a 500 `sort_not_wired` on such a row, naming the key and the class. A JSON-mode or custom key has no such set. Select them beside your columns, `db.select({ ...columns, ...built.extras })` or `findMany({ extras: options.extras })` (`applyListQuery` does it for you), and pass the rows with the built query to `queryHelpers.paginate(rows, built)`, which strips them. To put them into raw SQL, render each as `` sql`${extra.sql} AS ${sql.identifier(extra.fieldAlias)}` ``: interpolating the aliased extra itself renders only its quoted name, which SQLite reads as the string `'_cursorId'`. Rows that lack one the builder selected are a 500 (`page_not_wired`) naming it, on every page, so a forgotten count or flag is never read as none. An offset page reports the total (`0` for an empty first page). On one database a page past the end reports `null`, since no row carried the count and knowing it would take a second query; a merged page past the end reports the total, as every shard counted from its first row. A cursor page reports `null` too, and selects no count: a `count(*) over()` window would make the database read every remaining row on each page, which is the cost keyset pagination exists to avoid (and on D1, rows read are billed). The tiebreak id keeps its JSON type in the cursor, so a numeric id compares as a number even when it is an expression with no column affinity. Every value a cursor carries must be a string, number, bigint, boolean, `null`, date or bytes, and one its column holds; anything else is `invalid_cursor`. No list mints a cursor its next page refuses: a page that serves a row whose key its column does not hold, such as a JSON-mode key, answers a 500 `sort_not_wired` naming the key, and a SQLite column holding a class its mode reads as another, a `TEXT` column holding a BLOB or a number column holding TEXT, pages where the list reads the key back, as above. A number holds ±Infinity and NaN too, as a Postgres `double precision` or a SQLite `REAL` may. A Postgres `timestamp`, `timestamptz` or `date` in date mode pages exactly where it holds `'infinity'` or `'-infinity'`, which node-postgres reads as 2000-01-01 local time on a `timestamp` and as a Date no JS Date holds on the other two: the cursor binds the text the list carried, so it resumes where its row stood, deleted or not. A SQLite timestamp holding ±Infinity, or a finite value past the range a JS Date holds, reads as such a Date on bun:sqlite and libsql (D1 reads ±Infinity as null, above). A list that reads the key back from its anchor row carries that Date as itself, never as the null group, and reads its bound from the row: exact while the row is there, and once it is deleted, the list resumes from the direction's own end, repeating rows and skipping none. Any other list carries the stored value, as above.

import { createCursor, MIN_CURSOR_SECRET_BYTES, readCursor, sortSignature } from "@workerstack/database/query"

## Zod schemas

`createListQuerySchema()` declares what an endpoint permits and returns the Zod schema that parses the raw query string into what `buildListQuery()` takes:

<!-- ts-context
declare const request: { query: Record<string, string> }
-->

```ts
import { createListQuerySchema } from "@workerstack/database/query"

const postQuery = createListQuerySchema({
	filter: { created_at: "date", minute_read: "number", status: "enum", title: "string" },
	sort: ["created_at", "title"],
	search: ["title"], // publishes and accepts `q`
	fields: { scalars: ["id", "title", "created_at"] }, // publishes and accepts `select`
	lang: true, // publishes and accepts `lang`
	pagination: { defaultLimit: 20, maxLimit: 100, maxPage: 10_000 },
	limits: { maxConditions: 20, maxDepth: 3, maxInValues: 50, maxValues: 60, maxSearchTerms: 8, maxSortKeys: 3 },
})

const parsed = postQuery.parse(request.query)
```

The object is strict and each optional parameter exists only when the endpoint honors it: `filter` needs at least one filter field, `q` needs `search`, `select` needs `fields`, `lang` needs `lang: true`. Anything else is a 400 — a parameter the handler would ignore can no longer answer with the unfiltered list. Declaring `search` obliges the handler to pass a resolver: `buildListQuery()` throws `search_not_wired` on a `q` it has no resolver for.

`tiebreak` names the column the list breaks ties on, published on `x-database` as `stableTiebreak` for a client that walks pages; it defaults to `id`, the property `buildListQuery` breaks ties on, and a derived list whose `idColumn` is another column names that column's name. An empty `tiebreak` is a `TypeError`. The parsed output carries it as `tiebreak`, and `buildDerivedListQuery` holds its `idColumn` (or its anchor's) to it: a column of another name is a `TypeError` at build that names both, as the list would break ties on one column and publish another.

`page` runs from 1 to `pagination.maxPage` (10 000 by default, published as `maxPage` on `x-database` and as the param's `maximum`); past it a client pages by cursor, as an offset that deep makes the database skip every row before it. A page past `maxPage` throws `DatabaseError` `page_too_deep` (400) from `parse`, `safeParse` and `~standard.validate` alike, as `readCursor` throws `invalid_cursor`, so it reaches your error handler with the key a list no schema bounded answers; `safeParse` does not return it as an issue. A page that is no whole number from 1 in decimal digits (`0`, `1.5`, `0x10`, `1e3`) throws `invalid_page` (400) the same way, as `buildListQuery` and `paginate` answer it. `limit` takes decimal digits too, and any other spelling stays a validation issue. Leading zeros may pad either only up to the digits of its maximum, `maxLimit` or `maxPage` (`005` for a limit of at most 100, `00005` for a page): a longer padded count is `invalid_page` for a page and an issue on `limit`, so the query string a list takes stays within `maxQueryBytes`. A limit no schema checked, one an app writes itself, is held to a whole number from 1 by every list builder, as a page is, or it is `invalid_page` (400) naming the limit. A `maxPage` whose last offset, `(maxPage - 1) * maxLimit`, would pass 2^53 - 1 is refused when the schema is built. So is a `maxLimit` that is no whole number from 1, or a `defaultLimit` that is no whole number from 1 to `maxLimit`, each a `TypeError` naming the key; a `maxLimit` below 20 given alone needs a `defaultLimit` too, as the default of 20 would pass it. `extend` adds params of your own, validated and returned as they are; it may not take a name the schema owns (`cursor`, `filter`, `filterAst`, `lang`, `limit`, `limitBound`, `order`, `page`, `pageBound`, `parsedFields`, `parsedSort`, `q`, `select`, `sortOrderBy`, `tiebreak`, `validated`), which the type refuses and the builder throws a `TypeError` for, since an extension under one would replace a value the schema checked.

The `filter`, `order`, `q`, `limit` and `select` descriptions, examples and the `order` pattern are generated per endpoint from the same config (`filterParamMeta()`, `orderParamMeta()`, `searchParamMeta()`, `limitParamMeta()`, `selectParamMeta()`), and `cursor` publishes no example, so a spec lists the real fields, types, operators and limits even after a publisher strips `x-*`. The schema also carries the `x-database` query facts — `filterFields` with operators, `sortable`, `nulls`, `searchable`, `selectable`, and the limits, the byte caps `maxFilterBytes` and `maxSearchBytes` among them — see `packages/core/docs/meta-contract.md`.

`createRetrieveQuerySchema()` is the single-resource counterpart: `select`, and `lang` when its config says `lang: true`. It is strict too, so a `filter` sent to a single-resource endpoint is a 400 rather than a 200 that ignored it, and its `extend` may not take `lang`, `parsedFields` or `select`. `paginationResponseSchema` is exported for the response envelope. A list request is validated by `createListQuerySchema()` alone, and `buildListQuery()` refuses a filter or sort that did not come through it (see [SQLite SQL generation](#sqlite-sql-generation)).

## SQLite SQL generation

<!-- ts-context
import { integer, sqliteTable, text } from "drizzle-orm/sqlite-core"
declare const db: import("drizzle-orm/libsql").LibSQLDatabase
declare const parsed: import("@workerstack/database/query").ListQueryOutput
declare const env: { CURSOR_SECRET: string }
const post = sqliteTable("post", { _search: text("_search"), created_at: integer("created_at"), deleted_at: integer("deleted_at"), id: text("id").primaryKey(), title: text("title") })
-->

```ts
import { applyListQuery, buildListQuery, likeSearch } from "@workerstack/database/query/sqlite"
import { queryHelpers } from "@workerstack/database/query"
import { getTableColumns, isNull, sql } from "drizzle-orm"

const result = buildListQuery({
	cursorScope: "post:list", // the list: its route, and its tenant where it has one
	cursorSecret: env.CURSOR_SECRET, // opens a cursor's seal
	parsed, // postQuery.parse(request.query)
	table: post,
	baseWhere: isNull(post.deleted_at), // ANDed in — soft deletes, tenant scoping, access rules
	search: likeSearch(post._search), // a column searchText(title) wrote
	computedSorts: { popularity: (dir) => sql`view_count ${sql.raw(dir)}` },
})

const rows = await applyListQuery((extras) => db.select({ ...getTableColumns(post), ...extras }).from(post), result)
const [items, pagination] = queryHelpers.paginate(rows, result)
```

`parseFilter()` keeps filter values as strings; `validateFilter()` and the list query schema type them, so declared `number` and `date` fields bind as numbers and `boolean` as booleans, and a computed resolver receives the declared type. `buildListQuery()` and `filterToSQL()` expect that validated AST. A condition they cannot run, a computed field without a resolver, a resolver that returns `null`, a relation field with no `relations` entry, throws `filter_not_wired` (500) rather than being dropped, which would answer with more rows than the filter asked for. A sort field the table has no column for, or a computed sort without a resolver, throws `sort_not_wired` (500) the same way.

A filter on a relation field (`tags.slug`, through a `relations` entry) asks about the related rows: `eq`, `in`, `like` and the other positives match a row that has a related row matching, and the negatives match a row that has none matching their positive, so `tags.slug.ne.red` is a post not tagged red, an untagged one included, and never a post `tags.slug.eq.red` matches. `nin` is no related row in the list, `is.null` no related row with a value (an untagged post among them), and `is.notnull` no related row without one.

`buildListQuery()` returns `{ extras, where, orderBy, limit, offset, search, meta, pagination }` — it builds clauses, it does not execute. `extras` are the columns `paginate` reads, selected beside yours; `pagination` is what `paginate(rows, built)` reads to page them. `applyListQuery(select, built)` is the one supported wiring: it makes your select over the extras and chains the rest onto it. A select you wire by hand, to interleave joins, must apply all of it: select `built.extras`, and chain `.where(built.where)`, `.orderBy(...built.orderBy)`, `.limit(built.limit)` and `.offset(built.offset)`. A select that forgets `.offset()` serves page 1 for every page, and one that forgets `.orderBy()` pages rows in no order; database cannot see a select it did not make. `meta.type` tells you whether cursor or offset pagination won (cursor takes precedence), and `limit` is always one past the page, `parsed.limit + 1`, so `paginate` can tell there is a next page.

`buildListQuery()` and `queryHelpers.listOptions()` take a filter and an order only from the list query schema's output, which carries `validated: true`. A hand-built `filterAst` or `parsedSort` without it is refused (`filter_not_wired` / `sort_not_wired`, 500): checked against nothing, it could name any column of the table, `password_hash` included. Code that validated a filter against its own fields, as `validateFilter()` does, sets `validated: true` itself. The flag covers the filter and the order, never the page: a page is always a whole number from 1, and past the default `maxPage` (10,000) it is `page_too_deep`, unless it carries a `pageBound`, which the schema sets to the `maxPage` it was built with; then that number holds it. A limit is held the same way: past the default `maxLimit` (100) it is a 400, unless a `limitBound` states another. Each comes from the schema's config, never from a request, and a parsed query with a field changed stays held to them. Either on an input you make by hand is your app stating its own bound. `buildDerivedListQuery()` needs no flag: its caller passes the filter as SQL and maps every sortable field to a column.

`buildDerivedListQuery()` handles queries over a subquery or CTE, where sort columns come from a `sortColumns` map rather than the table. A derived list whose rows are one table, its sort columns that table's, names it as `anchor: { table, idColumn }`: a value too long for a cursor then goes by reference and is read back from that table, as on the table's own list. With `idColumn` alone no row holds its keys, so such a value is a 500 (`sort_not_wired`) on a page served by cursor that meets it, and so is a sort key SQLite stores as INTEGER that the driver read as a number past ±(2^53 − 1), rounded (D1 always, bun:sqlite by default), which the next page would seek by; a REAL past 2^53 is a double on disk, read back exactly, and pages. On Postgres the same holds by type: a `bigint` read as a number past 2^53 is the 500, and a `double precision` or `real` pages. A page by number serves such a row: when it is the page's last row, the one its next cursor would be minted from, its `nextCursor` is `null` while `hasMore` still says there is a next page by number. A `numeric` read in number mode is read as the nearest double, so 0.1000000000000000001 and 0.1000000000000000002 both read as 0.1: every list, derived or not, carries its text in `_cursorKeyTexts`, and the cursor binds that text as a `numeric`, exact whether or not its row is still there. Any other number under a type no double names, such as a domain's read through `mapWith(Number)`, is the 500 when it isn't a safe integer. Read such an integer as bigint, or name the `anchor`, whose row the keyset reads the exact key back from. A derived list must not dedupe with `DISTINCT`: SQL counts `_total` before `DISTINCT` runs, so the count would be the joined rows. Express such a join as `EXISTS` in `filterWhere`, or `GROUP BY` the id, which the count runs after. The list's database is read from the columns its id and sort columns hold, wherever an expression holds them; a list of SQL expressions alone, such as a union whose id is `` sql`inbox.uid` ``, states it with `dialect: "postgres"` or `dialect: "sqlite"`, and is a TypeError naming `dialect` without one, since Postgres types a key by its operand and SQLite by its storage class. A SQLite derived list whose rows sit on several shards, such as a union of two joined selects per shard, takes `merged: {}` (with `maxRowsPerShard`, as `buildListQuery`'s does): read each shard with `applyListQuery` and page the reads with `paginateMerged`. Its rows carry each sort field under its name, which the merge orders by, and it takes no `anchor`, as a merged list reads no key by reference. A merged Postgres derived list is a TypeError at build: the merge orders as SQLite does, while Postgres orders a `numeric` or `bigint` read as a decimal string, and text under the server's collation, in ways no in-memory merge can know.

`queryHelpers.paginate(rows, built)` takes the rows and the query that read them, any of the three builders' results (a merged list's goes to `paginateMerged`), and returns `[items, pagination]`; the built query's `pagination` says what it read, so nothing is passed twice. A list ordered by a computed sort, or a table with no tiebreak column, has no cursor to resume it: its `nextCursor` is `null` while `hasMore` still says there is a next page by number. More rows than the built query reads, one past the page, are a 500 (`page_not_wired`): rows a query read without its limit and offset are no page of this list. Underneath, `filterToSQL()` and `conditionToSQL()` are exported for advanced use, along with `orderSQL()` / `orderByKeys()` / `keysetSQL()` — the one ordering and keyset implementation every builder shares — and `patternToSQL()` for `like` / `ilike`.

Search comes in two flavours. `likeSearch(column)` is the portable fallback: it targets a `_search` column (or any SQL expression, such as `sql.raw('"_search"')` on a table drizzle does not declare), folds each whitespace-separated term with `searchText()`, finds it with `instr` in the expression's `lower()`, so no LIKE pattern meets D1's 50-byte cap, and ANDs the terms. A raw expression, such as a `title` column, is matched by ASCII case only: its accents and the other folds below match only in a column `searchText` wrote, so `café` and `cafe` both miss a raw `Café`. Write the column with the same function, `searchText(title, body, …)`, so the stored text and the query cannot drift apart: a column filled by SQL `lower()` misses every accented query. Its format, which a backfill must reproduce: the parts present joined by one space, NFKD-normalized (so ＦＩＬＥ and ﬁ fold), lowercased, Greek final sigma ς written σ (so an uppercase query ending in Σ finds the word), combining marks (U+0300–U+036F) removed except those that make a Cyrillic letter of its own, which NFC puts back into one letter (й, ї, ё, ў stay apart from и, і, е, у; a stress mark, as in доро́га, goes), Hebrew points and cantillation (U+0591–U+05C7), Arabic harakat and Quranic marks (U+0610–U+061A, U+064B–U+065F, U+0670, U+06D6–U+06ED) and the tatweel (U+0640) removed, so שָׁלוֹם is שלום and مـحـمّد is محمد, the Latin letters with no decomposition spelled in ASCII (ß ss, æ ae, œ oe, ø o, ł l, đ d, ð d, þ th, ı i, ĸ k, ŋ n, ŧ t, ħ h), then NFC-composed again, so й and Hangul syllables stay whole. Greek accents fold (ά is α). A change to this format means rewriting every `_search` column; 0.11 changed it, and "Upgrading to 0.11" says how to refold. `refoldStatements(table, column, sources)` from `@workerstack/database/query/sqlite` is that rewrite: its `select` reads each row's rowid, its sources and the text it stores, and `updates(rows)` gives one `UPDATE` per row whose fold differs, so a second run writes nothing. Run the select, then the updates in batches your driver takes (`db.batch` on D1). It needs the table's rowid. `buildFtsMatch()`, `buildFtsWhere({ table, ftsTable }, q)`, and `buildFtsHighlight()` target the FTS5 tables the `fts` generator created, and `buildFtsWhereWithSpellfix(db, { table, ftsTable, spellfixTable }, q)` adds spellfix1 fuzzy matching where the extension is available. It asks each database client once, before any spellfix query, with `editdist3`, the function spellfix1 registers, which reads no table: without the extension (stock bun:sqlite and libsql) the terms are searched as typed, and with it a missing or misspelled spellfix table, or a transient driver error, is thrown. The answer is kept per client a drizzle wrapper holds (`db.$client`), so a server that builds a wrapper per request asks once per client. D1 loads no extension, so a D1 client, the binding or a session `openD1Session` opens per request, is never asked and its terms are searched as typed. `spellfix: false` asks nothing and searches the terms as typed, for any other database that never has the extension. Every term becomes a bound prefix phrase, `"term"*`, so `post` finds `postgres`; FTS5 syntax in user text (`*`, `:`, parentheses, `AND`/`OR`/`NOT`) is quoted, never interpreted: inside its quotes every word and character of a term is searched as text, so `not found` needs both words and `error:timeout` finds that text. `sanitizeFtsTerm()` is the per-term cleaning: it removes control characters and skips a term with no letter or digit, which no token matches and which would otherwise empty the search. The FTS table name is a single identifier, quoted with `quoteIdent`. The generated FTS tables are keyed by their content table's `rowid`, so `buildFtsWhere` emits `<table>.rowid IN (SELECT rowid FROM <fts> WHERE <fts> MATCH ?)`: the rowid is qualified by the drizzle table you pass, so a join cannot make it ambiguous and a text `id` column never stands in for it. FTS5's `unicode61` tokenizer folds less: not ß to ss, æ to ae, a ligature such as ﬁ, halfwidth kana or a Greek accent. So an FTS table over the raw text misses a query typed in one of those folds, and one over a `searchText` column misses a query typed as written, unless the source says so: `buildFtsWhere({ folded: true, ftsTable, table }, q)` (and `buildFtsWhereWithSpellfix`, and `buildFtsMatch(name, q, { folded: true })`) folds each term with `searchText` first, so FTS over `_search` applies the folds `likeSearch` applies, per token prefix. It still finds less in two ways. FTS matches a term at the start of a token, where `likeSearch` matches a substring anywhere: `asse` finds no `reassess`, and a term inside an unspaced CJK, Thai or Hangul run (`都庁` in `東京都庁`, `국어` in `한국어`) finds no row, as the run is one token. And FTS drops symbols, which `unicode61` does not index, so `c++` searches `c*` and finds every row with a word that starts with c.

## Translations

`resolveTranslation()` picks one row out of an array of translation rows: the requested `lang`, else `defaultLang`, else the first available. It returns that row's fields under that row's own language code, so fallback content is never labeled as the requested language, and a field the row lacks stays empty rather than being filled from another language. `fields` narrows the returned keys (`null` keeps all), and `languageCodeKey` names the discriminator column (default `languageCode`). It is pure and dependency-free, so it runs equally well over rows Drizzle already loaded via `with`.

<!-- ts-context
declare const post: { post_translation: Array<{ body: string; languageCode: string; title: string }> }
-->

```ts
import { resolveTranslation } from "@workerstack/database/query"

const localized = resolveTranslation({
	translations: post.post_translation,
	lang: "pt-BR",
	defaultLang: "en",
	fields: ["title", "body"],
})
```
