# Migrations

## Config and providers

```ts
/* database.migrate.config.ts */
import type { MigrateConfig } from "@workerstack/database/migrate"

export default {
	databases: {
		core: {
			migrationsDir: "./atlas-migrations",
			drizzleConfigPath: "./drizzle.config.ts",
			name: "core",
			provider: { type: "bun-sqlite", path: "./.database/core.db" },
		},
	},
} satisfies MigrateConfig
```

The config imports database's type alone, as `migrate init` writes it: the import erases, so the config loads where `@workerstack/database` does not resolve, as in an app built with `bun build --compile`, whose embedded database no project file can import. A config that imports `defineConfig` fails there, and the error names this form.

The config is Zod-validated when database loads it, so a typo fails at load rather than at apply, with one message that names the file and the key, whether it is exported through `defineConfig` (which only types it), as a plain object, or as a function, sync or async, that returns one; a function that returns a function is refused, naming the form below (a program that imports its config module instead calls `await parseConfig(imported)`, on either form, the one parse `loadConfig(path)` runs, since `defineConfig` checks nothing at run time): every object is strict, and a key database does not know is refused by name. `diff`, `apply`, `check` and `status` all take a database by its name here; a database whose tables and FTS live under another name in `database.config.ts`, as two shards of one schema do, says so with `codegen: "shard"`, and `diff shard-0` reads that database's FTS. Each `provider` is a discriminated union on `type`: `bun-sqlite` (`path`), `libsql` (`url`, `authToken?`), `turso` (`databaseName`, the Turso database's own name, `org`, `apiToken`, and `group`, default `default`), `d1` (`databaseName`, the wrangler config's `database_name` or binding; wrangler finds the database through its config), `postgres` (`url`, with `devUrl`, `schema` and `lockTimeout` defaulting to `docker://postgres/17/dev`, `public` and `5s`). There is no `neon` type: a Neon or Supabase database is a `postgres` URL. A database is one of two shapes, held at load: one target, with its `name` and `provider`, or `environments`, at least one, chosen by `-e`, each named by its key unless it gives a `name` and taking the database's `provider` unless it gives its own; a database with both a `name` and `environments`, or an environment with no provider at either level, is refused. Every environment of a database has its dialect, and `-e` on a database that declares no environments is refused. A `postgres` `url` is checked when a command resolves its environment, not at load, so a production URL unset in this shell blocks no command on `-e dev`, and `diff`, which reaches only `devUrl`, needs none. `migrationsDir` and `drizzleConfigPath` are read relative to the config file, by `diff` as by `apply`.

A database migrated in more than one place declares `environments` instead, and every command on it names one with `-e`. Here `core` is the D1 database the wrangler config beside the migrate config binds: `dev` is the local copy wrangler keeps under `.wrangler/`, and `prod`, which takes the database's provider, is the remote one:

```ts
/* database.migrate.config.ts */
import { defineConfig } from "@workerstack/database/migrate"

export default defineConfig({
	databases: {
		core: {
			migrationsDir: "./atlas-migrations",
			drizzleConfigPath: "./drizzle.config.ts",
			provider: { type: "d1", databaseName: "core" },
			environments: {
				dev: { provider: { type: "d1", databaseName: "core", local: true } },
				prod: {},
			},
		},
	},
})
```

The wrangler config beside it needs the binding with `migrations_dir` set to database's `migrationsDir`, which database checks before it applies; a Worker's `database_id` goes here too:

```jsonc
// wrangler.jsonc
{
	"d1_databases": [
		{
			"binding": "DB",
			"database_name": "core",
			"migrations_dir": "atlas-migrations",
		},
	],
}
```

```bash
bunx database migrate diff core add_post_slug -e dev
bunx database migrate apply core -e dev
bunx database migrate check core -e prod
bunx database migrate apply core -e prod
```

The function form, for a config that reads its secrets when database loads it: the function calls `defineConfig`, so TypeScript holds the object written inline to its known keys here too, and a misspelled `local` or `migrationsDir` fails to compile. `defineConfig` takes no function:

```ts
/* database.migrate.config.ts */
import { readFile } from "node:fs/promises"
import { defineConfig } from "@workerstack/database/migrate"

export default async () =>
	defineConfig({
		databases: {
			core: {
				migrationsDir: "./atlas-migrations",
				name: "core",
				provider: {
					type: "libsql",
					url: "libsql://core.turso.io",
					authToken: (await readFile("./.secrets/core-token", "utf8")).trim(),
				},
			},
		},
	})
```

A Postgres database is a URL, with the dev database Atlas replays migrations on beside it:

```ts
/* database.migrate.config.ts */
import { defineConfig } from "@workerstack/database/migrate"

export default defineConfig({
	databases: {
		analytics: {
			name: "analytics",
			migrationsDir: "./pg-migrations",
			drizzleConfigPath: "./drizzle.pg.ts",
			provider: {
				type: "postgres",
				/* direct, not pooled, and verified: Neon's host without -pooler, Supabase's direct or session port 5432 */
				url: process.env["DATABASE_URL"] ?? "",
				devUrl: process.env["ATLAS_DEV_URL"] ?? "docker://postgres/17/dev",
				schema: "public",
				lockTimeout: "5s",
			},
		},
	},
})
```

- `url` reaches database's Atlas runs only through their environment, never the command line, and database checks it first: an unescaped `#`, `/`, `?` or `@` in the password is refused by field name, and every line of Atlas output database relays is scrubbed of passwords and secret query values. `PG*` variables in your shell (`PGSSLMODE`, `PGPASSWORD`) are ignored, `~/.pgpass` and `~/.pg_service.conf` are not read, and a URL naming a libpq `service` is refused, so the config is the only connection; a URL without a user is the OS user's, as libpq reads it. A libpq key Atlas's driver would send the server as a setting is dropped from the URL Atlas gets when it only tunes the connection (`keepalives` and its `_count`, `_idle` and `_interval`, `gsslib`, `sslcompression`, and `channel_binding` or `gssencmode` other than `require`), and refused by name when it asks for what Atlas cannot do (`channel_binding=require`, `gssencmode=require`, `require_auth`, `requirepeer`, `sslcrl`, `sslcrldir`, `sslpassword`). `sslrootcert=system` verifies with `sslmode=verify-full`, which it implies, as libpq does, against the CAs Atlas's driver reads: on Linux the system's CA files (`SSL_CERT_FILE`, else the distribution's bundle, and `SSL_CERT_DIR`, else `/etc/ssl/certs`); elsewhere Node's own system store (Node 22.15 and later), or, under Bun or an older Node, the runtime's bundled CAs, which a verification failure names. A TLS file is checked only under an sslmode that reads it (`require` and the `verify-` modes, or none), and an encrypted `sslkey`, which Atlas's driver cannot read, is refused with the `openssl pkey` line that decrypts it, as is an `sslcert` without its `sslkey`, which libpq and Atlas's driver refuse. database warns when a host off the machine (anything but `localhost`, 127.0.0.0/8 or `::1`) is reached with `sslmode=disable`, `allow` or `prefer` (a URL with none is `require`), and on a Neon `-pooler` host or Supabase's port 6543: a transaction pooler drops the session lock Atlas holds. A URL naming several hosts is refused, as database migrates one database, and so is a `passfile` libpq would ignore (not a plain file, or readable by others) when the URL has no password.
- `devUrl` is an empty database Atlas may wipe; it must not be `url`. The default, `docker://postgres/17/dev`, needs Docker; match its major version to your server. On a `postgres://` `devUrl`, `check` and `baseline` replay the history in a database of their own on its server, made from `template0` for one run and dropped after it, so its role needs `CREATEDB`, and `CREATEROLE` when the history creates a role devUrl's server lacks; a role without either is refused, naming the privilege. That database takes the target database's encoding and locale (its provider, collation and character type, and its ICU or builtin locale and ICU rules), read from `url`, so a text range partition, a `CHECK` on text order or a seed checks as apply runs it whatever the server's default is; a `devUrl` server that cannot make that locale stops the run, naming it, since a verdict under another locale is not the target's. The extensions `devUrl`'s database holds are made there first, each in its schema at its version, so the role must be able to create them too; one a replayed file creates with a plain `CREATE EXTENSION` is left to that file, so it checks as apply runs it, and one that requires it is made right after; a file's `CREATE EXTENSION IF NOT EXISTS` finds its extension made, as on a target whose platform installed it. A check stopped by Ctrl-C or `SIGTERM` drops its database and the roles it made first, then exits as the signal would. One killed outright leaves them, and the next `check`, `baseline` or `apply` on that server drops them at once: each is named for the backend that made it, and goes once that backend is gone, so a run never touches a live run's database, nor one anybody else is connected to. A statement the killed run left running, such as a long backfill, is its own: the replay's connections carry its name as their `application_name`, and the sweep ends them before it drops the database; on Postgres 14 and later such a statement also ends by itself within a second, as the replay asks the server to check that its client is there. A superuser `devUrl` drops what any role's runs left; any other role drops only the databases it owns or is a member of the owner of, and the roles it made. `apply` sweeps only when the target's server holds something a killed run left, so a `devUrl` the deploy cannot reach costs nothing; then it waits at most 5 seconds for `devUrl` (unless the URL sets `connect_timeout`), and when that fails it says so and applies anyway. A drop that fails is left to a later run and never changes the verdict. A role the history creates is made `NOLOGIN NOSUPERUSER NOREPLICATION NOBYPASSRLS`, in no role the replay did not make, since the replay needs only its name; check says so for each `CREATE ROLE` or `CREATE USER` that asked for more, and apply alone gives it the rest. A later statement on roles the replay made runs too, as their drop undoes it: a `GRANT` of one, a rename, `ALTER ROLE` (without a login, a password or those attributes, which check says), `ALTER GROUP`, `ALTER ROLE … SET`, `DROP ROLE`, `DROP OWNED` and `REASSIGN OWNED`; one on a role another database holds is left out. A `CREATE TABLESPACE` is left out, and a table or an index a later statement puts in that tablespace is made in `pg_default` instead; check says so for each.
- `schema` is the one schema database migrates. Both URLs are scoped to it (`search_path`; a URL that names its own `search_path` must name this schema), and Atlas keeps its history outside it: `public`'s in `atlas_schema_revisions`, any other schema's in its own `atlas_schema_revisions_<schema>`, so two schemas of one database, each migrated by its own config, never share a history. A schema name that is not plain lower case, or would pass Postgres's 63-byte limit, is named by its hash. An object the drizzle schema puts in another schema, a Supabase `auth.users` reference included, is an error. A schema other than `public` must exist on both databases, and your app's `search_path` must match.
- `lockTimeout` bounds how long a statement waits for a lock (`0` for no bound), so an `ALTER` behind a long reader fails instead of queueing every later query. database sets no `statement_timeout`; add one to the URL's `options` if you want it.

`loadConfig()`, `resolveDatabaseConfig()`, and `createProvider()` turn that into a `ConnectionProvider`. Each provider exposes the same `Connection` interface, and the SQLite introspection reads it: `introspectSqliteSchema`, `getSqliteTables`, `getSqliteColumns`, `getSqliteIndexes`.

## Diff and apply

On the first config under [Config and providers](#config-and-providers), a bun-sqlite database, the cycle is:

```bash
bunx database migrate init
bunx database migrate diff core add_post_slug
bunx database migrate apply core --dir ./atlas-migrations
```

`diff` runs the project's `drizzle-kit export`, on the runtime running database, to dump the desired schema, hands it to Atlas, and writes a timestamped SQL file.

FTS5 tables stay out of what Atlas sees, because its dev SQLite has no fts5 module. Atlas replays a copy of the history with the FTS statements stripped and diffs a target without them. database then appends the FTS part itself: for each FTS table whose definition changed, or whose content table Atlas rewrote (SQLite drops a table's triggers with it), it drops the triggers and the virtual table, creates them from the config, and runs `INSERT INTO <fts>(<fts>) VALUES ('rebuild')`. A database the config declares must load: a broken `tables` file is an error, not a diff without FTS. Since Atlas only ever sees the copy, database checks the real `atlas.sum` against the files first.

A migration's hash is its SQL with comments and layout normalized away, never the text inside a literal. Files recorded under the pre-0.5.0 hash, which stripped `--` even inside literals, still count as applied, on SQLite, libsql and D1 alike.

`apply <db>` takes its database from `database.migrate.config.ts` when the project has one: `-e/--env` picks the environment, whose provider supplies the connection, and `migrationsDir` is read relative to the config file. Without a migrate config, `<db>` is a D1 binding in the working folder's wrangler config, remote by default and local with `--local`. A Postgres database goes through Atlas ([Postgres](#postgres)). On every SQLite database, apply first checks, and applies nothing unless every pending file passes:

1. The directory matches its `atlas.sum`.
2. A file is pending unless the history records it: its hash, current or pre-0.5.0, in `__drizzle_migrations`, or on D1 its name in the binding's `migrations_table` (`d1_migrations`). A pending file that sorts before an applied one is refused, since it would run after files written later.
3. Each pending file is classified against the schema the earlier files leave: `parseMigration()`, `classifyMigration()` and `extractDropStatements()` read each statement, and each action of an `ALTER TABLE`, through quoted and schema-qualified names, and rate the file:
   - **unsafe** loses data or breaks deployed code by name: dropping a table, column, schema, type, sequence or role, `CASCADE`, changing a column's type, `SET NOT NULL`, adding a `NOT NULL` column without a default, renames, `TRUNCATE`, `DELETE` or `UPDATE` without a `WHERE`, an FTS5 `'delete'` or `'delete-all'` command, a statement database does not recognize, and every trigger, function, procedure or rule made, replaced, altered or dropped, and every `DO` block, which database names by that rule ("database rates every trigger change unsafe") whatever else it reads of them, and on SQLite every pragma database does not write itself (all but `foreign_keys` and `defer_foreign_keys`), named the same way. On Postgres a `COPY` that runs a program or writes a server file is unsafe. An `EXECUTE`, bare, under `CREATE TABLE AS` or behind `EXPLAIN ANALYZE`, is rated by the statement its file prepared before it; one whose name a statement before it in its file may have prepared by running user code is unsafe, naming that code: a trigger an `INSERT`, `UPDATE`, `DELETE` or `SELECT` may fire or call, an event trigger a DDL statement fires (a `CREATE TABLE AS` fires its own before its `EXECUTE` runs), a `DO` block, a `CALL`, a function call, or another `EXECUTE`. Atlas cannot run a `COPY FROM STDIN` or `TO STDOUT` at all, so check refuses one, and no approval clears it. apply runs each file in a session of its own, so an earlier file's `PREPARE` never reaches it, and check refuses an `EXECUTE` that nothing before it in its file may have prepared, past any approval too: one with only a `PREPARE` of another name, a `DEALLOCATE`, a transaction statement, a `SET` or a `SHOW` before it. An unsafe file runs only after a yes on a terminal, or when the file approves itself with a line of its own, `-- database:allow-unsafe: <reason>`, which goes through review with the file. `--yes` does not cover it, so a pipeline that always passes `--yes` cannot drop data unreviewed.
   - **cautious** drops nothing a row holds: indexes, constraints, defaults, views, a grant, a new owner (who bypasses row level security), a sequence reset by `setval`, rows a `COPY` loads from a server file. It runs with `--yes` or a yes on a terminal.

   What a statement writes is read from the engine, never from its spelling. On SQLite the proof run reads it (below). On Postgres database reads every statement with Postgres's own parser (libpg-query 17) and walks every node, so a write in a CTE, a subquery, a rule's action or behind `EXPLAIN ANALYZE` counts, and so does `UPDATE users*`, `U&"users"` or `"users"SET`:
   - a `DELETE`, a `MERGE` that updates or deletes, and an `UPDATE` or upsert of rows that were there before the file are unsafe; an `UPDATE` or upsert that only fills a table the file created, or only columns it added (once), is cautious;
   - a write to a table whose trigger the history holds fires it, and is unsafe;
   - a `TEMP` table or view, or one in `pg_temp`, that takes an existing table's name shadows it for the rest of the file, and is unsafe;
   - a `DO` block, a `CREATE FUNCTION`, `PROCEDURE` or `TRIGGER`, a `CALL`, and a call of any function that is not a pure built-in (`lower`, `now`, `gen_random_uuid`, `jsonb_build_object` and the like) run code database does not read, and are unsafe; `setval` is cautious, as is `nextval`, whose advance a rollback does not undo; `current_setting`, which copies a setting into what it writes, and `dblink` are unsafe;
   - a statement Postgres cannot parse is unsafe.
   - **safe** runs without asking.

   Without a terminal or an approval, `apply` stops before running the file. A SQLite table rebuild (Atlas copies the rows into `new_t`, drops `t` and renames `new_t`) is cautious when it copies every column the earlier files gave `t`, and unsafe when it leaves one out, which is how Atlas drops a SQLite column. A rebuild of a table other tables reference is unsafe unless it carries database's guard exactly as `database migrate diff` wrote it (see below); an edit inside the guard makes it unsafe again.

   On bun:sqlite, libsql and D1, `check` and `apply` also run a proof first. Each pending file runs on a private copy of the database's live schema, on the SQLite its files apply on (the runtime's for bun:sqlite, libsql's own for a libsql or Turso database, so a vector index is proven and syntax libsql's older SQLite refuses is refused at check), one statement at a time, each file on a fresh connection, as it applies. The copy holds what the pending files can observe: the objects they name, and the keys, indexes, triggers, views and virtual tables those reach, such as an fts5vocab table's FTS table or an FTS table's content table or view. When a file alters a table it also holds every view and trigger, since SQLite checks them all on a rename or a dropped column, and it holds the views and triggers that read a view a file names. After each file the proof compiles every view and trigger that survives it and uses something the file dropped or changed, since SQLite's `DROP TABLE` and `DROP VIEW` check none of them: a file that leaves one unable to run is refused, naming it and SQLite's error, and no approval overrides it. When a file, or an object the copy holds, reads the schema itself through a `sqlite_` table (`sqlite_master`, `sqlite_sequence`, `sqlite_stat1`), a `pragma_` function or a `PRAGMA` statement, the copy holds every object and seeds every table. A pragma that only sets how statements run is no such read: `foreign_keys`, `defer_foreign_keys`, `legacy_alter_table`, `recursive_triggers`, `case_sensitive_like`, `ignore_check_constraints` and `busy_timeout`, so drizzle-kit's table rebuild, which turns `foreign_keys` off and on, holds only what it reaches. Otherwise only the tables a file names or its writes can reach, and the tables their keys need, get rows: six each, chosen so a change shows. database splits a SQLite file where SQLite ends a statement (its `sqlite3_complete()` rule): at a `;` in code, except inside a trigger's body, which ends at `END` and `;`, so a column or table named `begin` or `end` is a name wherever it stands. The copy's own SQLite then confirms each piece is one statement, and a piece it reads as more is refused, naming the file and the statement, since libsql's client runs only the first statement of a string. On bun:sqlite and D1 the copy is a file in a temporary directory only you can open, removed after the run; one a killed run left is removed by a later run. On libsql and Turso it is held in memory, so no file is left. Before each statement runs, SQLite itself (`EXPLAIN`) says what it writes to the tables that were there before the file. An update of a column they had, a delete of their rows (a `REPLACE` that meets one included), a trigger on them it can fire (its `WHEN` is not evaluated), an update, delete or replace of a virtual table's rows, and a temp table or view that takes one's name make the file unsafe, whatever rows the statement meets and however it is spelled. A backfill of only the columns the file added is cautious, and a write to a table the file created is safe. Then every table that was there before is compared, row for row, on the columns it had. A lost row, a lost column, or a value changed, copied between columns or moved between rows makes the file unsafe, and the reason names the table and column. The one allowance: a NULL that becomes the new default of a column the file made NOT NULL is cautious. A file the copy cannot run is unsafe, with the statement and why (or `COMMIT` and why, for a key the file deferred and left broken), and so is every pending file after it, which nothing then proves. A table database cannot seed is listed as unproven, with why. On Postgres, writes are rated from their text, and `check` lets Postgres decide what no database runs: on a `postgres://` `devUrl` it replays the history and the pending files there before any approval, as Atlas applies them: each file in a transaction of its own, a `-- atlas:txmode none` file statement by statement, each in a transaction of its own first, so the counts below refuse a change past its database before it commits, and bare, as Atlas sends it, where Postgres runs it only so, in a database of its own (see `devUrl` above). So a batched backfill that commits inside a `DO` block or a procedure passes, and a `LOCK TABLE`, `SAVEPOINT`, `RELEASE`, `ROLLBACK TO` or a cursor not held, outside the file's own `BEGIN`, stops `check` as it stops `apply`, named with Postgres's message while database rates the file, so on any devUrl. A statement the dev database refuses stops it, naming the file, the statement and Postgres's message (a retype of a column a view, a rule, a policy, a trigger's `WHEN`, a generated column or a `BEGIN ATOMIC` function reads). A statement whose scope is the server or another database is left out, and `check` names it: `ALTER SYSTEM`, `CREATE`, `ALTER` and `DROP DATABASE`, `ALTER` and `DROP ROLE`, `DROP` and `REASSIGN OWNED` and a grant or revoke of a role the replay did not make, a tablespace, a subscription, `CHECKPOINT`, `REINDEX DATABASE` or `SYSTEM`, a prepared transaction, a `COPY` to a server file or from a program, and an owner, comment, grant, rename or security label of a database, a role, a tablespace or a server parameter. So is a statement that runs a function acting on the server, named as a call of it: a replication slot's making, dropping or reading of changes, `pg_terminate_backend` and `pg_cancel_backend`, `pg_reload_conf`, `pg_switch_wal`, a statistics reset, `lo_export`, a replication origin's work, and every `dblink` function, whatever schema holds them, as a connection left out leaves its cursors and queries nothing to reach; a hidden call whose effect leaves no state database can read, such as an ended session or a written file, runs on devUrl's server; a definition that only names one (a view, a function, a trigger, a policy, `EXPLAIN` without `ANALYZE`) runs as written. A replication slot a `DO` block or a function makes is read from the server after the file, refused when the file names it, and dropped. A change a `DO` block or a function makes to the database it runs in, named by `current_database()` (a setting, a grant on it, its comment), is the replay's own, since the replay drops that database after it; making it a template or giving it another owner stays refused, as the replay could not drop it then. A `CREATE ROLE` runs, since a policy may need its role: a role the server already has is used as it is, and one the replay made is dropped after it. A grant or revoke of roles the replay made runs too, such as the `GRANT app TO CURRENT_USER` a role that is no superuser needs before `ALTER TABLE … OWNER TO app`, since dropping the role undoes it. So do a rename, `ALTER ROLE`, `ALTER GROUP`, `ALTER ROLE … SET`, `DROP ROLE`, and `DROP` and `REASSIGN OWNED` of roles the replay made that no other database holds; `ALTER ROLE` runs without a login, a password, `SUPERUSER`, `REPLICATION` and `BYPASSRLS`, and `check` says so. A table, an index or a materialized view a statement puts in a tablespace whose `CREATE TABLESPACE` the replay left out is made in `pg_default`, and `check` says so. A pending file that makes a role the target's server already holds, by `CREATE ROLE` or a rename to it, stops `check` as it would stop `apply`, with `role "<name>" already exists; apply would stop at <file>`: another database's apply on the same server may have made it. `check` reads the target's roles for this on a `docker://` `devUrl` too. A `DO` block, a function, `EXECUTE` and `CALL` run as written, and Postgres says whether one changed the server, twice. In a file that runs in a transaction, Postgres's own counts of the transaction's writes decide before its `COMMIT`: a file that changed a role, a membership, a database, a setting, a comment, a tablespace or anything else the server's databases share, past what the replay drops after it, is rolled back and refused, naming the file and the change. A role such a statement adds is the replay's to drop, as one its own `CREATE ROLE` made: the replay adopts it, makes it `NOLOGIN NOSUPERUSER NOREPLICATION NOBYPASSRLS` with no password before the file commits, and drops it after, and `check` says so for each, so the usual `DO $$ BEGIN IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'app') THEN CREATE ROLE app; END IF; END $$` passes. A change to a role the replay made or adopted is its own too: the role's options and password, a membership in it or of it, its settings and its comment or security label. A change to any other role stays refused. On a superuser's devUrl database reads `pg_authid`, so a password change is named as one (`role app changed (rolpassword)`) and the password itself is never read out; on any other devUrl a change its role cannot read, such as a role's password, is refused as one. A devUrl whose server keeps no counts for its role (`track_counts` off) is refused, naming the setting, and so is a file that turns them off. Around every file and every statement a `-- atlas:txmode none` file sends bare, database also reads the server's shared catalogs as committed, another replay's own rows left out. That sees what a bare statement changed, which no transaction counts, and what a second connection committed, such as `dblink_exec`'s `CREATE DATABASE` or `CREATE ROLE`, which the replay's own counts never see. A `txmode none` statement runs bare only where a block changes what it does: one Postgres refuses in a block (an outside-only statement such as `CREATE INDEX CONCURRENTLY` or `VACUUM`, or a `DO` block or procedure that commits), one Postgres runs only in a block (a `LOCK`, a `SAVEPOINT`, `RELEASE` or `ROLLBACK TO`, a cursor not held), and the file's own `BEGIN` and `COMMIT` and what runs between them. A change one of these makes past its database has committed by the time the read sees it, so `check` refuses it and names what devUrl's server keeps, which database cannot undo. These are the server's catalogs, not the replay's, so a change there is the file's only when the role, database or other object it is to is one the file names: unquoted (folded to lower case, as Postgres folds it), quoted, or inside a string a `DO` body, `dblink_exec` or `format()` may run; and only when the file's statements so far run code database cannot read, a `DO` block, a `CALL`, an `EXECUTE` or a call of a function outside `pg_catalog`, since a file of plain statements makes no such change unseen, and Postgres records no creator for a role, a database or a slot that could tell another session's from the file's. `CURRENT_USER`, `CURRENT_ROLE`, `SESSION_USER` and `USER` name devUrl's role, and `ALL` in `ALTER ROLE ALL` names every role, so a setting a `DO` block commits with `ALTER ROLE CURRENT_USER SET …` or `ALTER ROLE ALL SET …` is refused. Such a change is refused, naming the file, the statement and the change, and left on devUrl's server for you to undo there, since another session may have made it; database drops only the replay's own database and the roles it made. A change to any other object is another session's, and `check` passes it. A name the file builds at run time, by concatenation, from a query, or in a function another file defines, is not one it names, so `check` neither refuses nor drops that change. A role's password reads only from `pg_authid`, so a password a bare statement changes is seen only on a superuser's devUrl. This needs the `postgres` package; on a `docker://` `devUrl`, which database cannot reach, or without `postgres`, `check` says it did not replay and rates the files alone. The target is only read, and a file that changes the server is refused before anything reaches it.

4. On SQLite, libsql and Turso, database applies each file's statements, as written, and the insert of its hash as one batch, which every provider runs all-or-nothing. On a SQLite file (bun:sqlite, a libsql `file:` URL), each file applies on a connection opened for it and closed after it, as wrangler runs each file on D1, so a pragma a file sets on its connection (`ignore_check_constraints`, `recursive_triggers`, `legacy_alter_table`, `case_sensitive_like` and the like) ends with the file, and the next file runs as it would alone. A libsql server, which a libsql URL of any other scheme (`http`, `https`, `ws`, `wss`, `libsql`) reaches and which Turso runs, refuses those pragmas: it parses each statement first and runs only what it lists. So check holds a file for such a target to what the libsql server (sqld) runs, measured on the sqld database's tests pin, and refuses the rest with no override, naming the server: a pragma outside its list or with a quoted name (it runs `foreign_keys`, `defer_foreign_keys`, `user_version`, the `table_info` family and the checks, and reads most others), `ANALYZE`, `ATTACH`, a `TEMP` object and `load_extension()`. Turso cloud is held to the same set. With no connection setting left to end, a server's files apply through the one client the run writes with, and a Turso apply mints one token for it. An in-memory database (`:memory:`) lives in its one connection, so every file applies through that one. A pragma whose setting is the process's (`hard_heap_limit`, `soft_heap_limit`, `temp_store_directory`) reaches every connection and outlives the file, so check refuses it, with no override. Every SQLite provider applies with foreign keys on, as the proof runs: bun:sqlite, which SQLite opens with them off, turns them on for each connection database opens. A file is applied and recorded, or neither. A transient failure retries the whole batch through `withRetry()`, which reads it from the error's structured fields alone (on the error or a cause): an HTTP status of 429 or 5xx, or a network code such as `ECONNRESET` or `UND_ERR_SOCKET`. An error with a `SQLITE_` code is never retried, whatever its message says. On a SQLite file, a write lock that the app serving the file or a second runner holds is waited for rather than failed on: every connection database opens to the file sets `PRAGMA busy_timeout = 5000`, SQLite's own wait, which retries no failed statement, and each file's batch begins `IMMEDIATE`, taking the lock before any statement. Its record is written first, so a file another run applied while this one waited fails on its name before it runs anything, and is skipped as `Skip (applied by another run)`. `--file` applies one file on its own, which no sum or order covers.

On D1, wrangler applies. database reads the binding from the wrangler config with wrangler's own reader, refuses when its `migrations_dir` is not database's `migrationsDir` or its `migrations_pattern` takes anything but that directory's `.sql` files, orders the files as wrangler does (by leading number, then name, so 8- and 14-digit prefixes mix), checks exactly the files wrangler will apply, and runs `wrangler d1 migrations apply` with stdin closed. wrangler runs each file and its `d1_migrations` row as one batch locally and one query remotely, and takes no backup, so bookmark a production database (Time Travel) before an apply. database then reads the table back and fails unless it holds exactly the files it checked, printing wrangler's own words; a declined prompt or a failed file leaves its row out. A file that landed in the directory while wrangler ran, which wrangler applied and database never checked, is named, and listed under `applied` in `--json`: check it against git, then run `database migrate baseline <db> --hashes`. `--file` does not apply to D1. D1's own engine refuses much a SQLite build runs: pragmas outside [Cloudflare's list](https://developers.cloudflare.com/d1/sql-api/sql-statements/), functions outside workerd's allowlist, virtual-table modules but fts5, fts5vocab, rtree and rtree_i32, TEMP objects, savepoints, `_cf_` names, and its limits. So check runs each pending file on D1's own engine: after the proof, on a scratch local D1 that the checked wrangler's Miniflare opens with the proof's copy and its rows, each file as wrangler sends it (its `splitSqlQuery`, with the `d1_migrations` row it appends), then compiles each view, and each table's writes, that the file made or changed, a view's writes only for the events its triggers fire on, since D1 resolves a function in a trigger, a view or a generated column only when a statement uses it. A file D1 refuses there is refused, naming D1's error, and no approval overrides it. When the local D1 itself crashes compiling a statement, database compiles it again on a fresh scratch D1; a second crash proves nothing about the live database, so the file is cautious, "unproven on D1's engine", and runs with `--yes` or a yes on a terminal. wrangler `--local` deletes the first `BEGIN TRANSACTION;` and `COMMIT;` of a file holding `BEGIN TRANSACTION`, inside literals and comments too, where a remote apply sends the text as written, so check refuses such a file; split the words, as in `'BEGIN ' || 'TRANSACTION'`. A database that database 0.7 migrated records its files in `__drizzle_migrations`; apply refuses it until `database migrate baseline <db>` copies that record into `d1_migrations` once. wrangler's table records names only, so database records each applied file's hash beside it and refuses a file applied, then edited. A name is in wrangler's table only once database holds its hash or its intent. Apply records each pending file's hash as an intent before wrangler runs, and moves it into database's hashes once wrangler's table names the file, so a recorded hash is always the text wrangler ran: an apply that fails or is lost leaves only intents, which the next apply clears, and a file wrangler applied while database lost the move counts as hashed while its text still matches its intent, until the next apply or `--hashes` records it. Baseline writes the hashes before wrangler's rows, so a call lost between them leaves nothing a rerun cannot finish. A rerun of baseline copies every file `__drizzle_migrations` records that lacks either row, so it also finishes a baseline a lost call left half done. A file applied before database recorded hashes has none, and `status` names it; once you have checked those files against git, `database migrate baseline <db> --hashes` records the current hash of each applied file that has none, after the same checks apply runs (it refuses while a name in the history matches no file, or a recorded hash is not its file's). Run it once; `--hashes` is for D1 alone, as every other history records each hash as it applies. A D1 database's history is in four tables, which a tool that empties a database must keep, rows and all: `d1HistoryTables(migrationsTable?)` from `@workerstack/database/migrate` names them, the binding's `migrations_table` first (`D1_MIGRATIONS_TABLE`, `d1_migrations`, by default), then `D1_HASH_TABLE` (`_database_migration_hashes`), whose loss lets an edited applied file pass `check`, `_database_migration_hash_intents`, the intents of an apply in flight, and `DRIZZLE_HISTORY_TABLE` (`__drizzle_migrations`, database's history before 0.8).

`baseline <db>` records the files as applied without running them, for a database whose schema was set up out of band, after Atlas compares the database's schema with the one the history leaves; any difference is printed and nothing is recorded. On SQLite database reads the schema from the database itself and compares FTS5 tables by name, since Atlas's dev SQLite has no fts5 module. On D1 it copies only what `__drizzle_migrations` records.

The circuit breaker (`createCircuitBreaker()` and its checks) is a library API for your own runners, such as a multi-tenant fan-out; the CLI does not use it, because one atomic batch per file already leaves nothing half-applied.

## Postgres

`diff` exports the drizzle schema with the database's `drizzleConfigPath` and hands Atlas the rest, on the dev database, scoped to `schema`. Atlas OSS refuses views, materialized views, policies, sequences, roles and extensions, so database keeps them out of what Atlas replays and diffs and writes their part of the migration itself, around Atlas's statements:

- first, new extensions (`CREATE EXTENSION IF NOT EXISTS`), roles and sequences, since a table may use them, and a changed sequence `ALTER SEQUENCE`d in place, never dropped (that would restart it);
- then the drops of every changed or removed view and policy, and of each one over a table Atlas alters, since Postgres refuses to retype a column a view or policy reads; a view over a dropped view goes first;
- after Atlas's statements, those views and policies created again from the schema, and removed sequences dropped.

Roles and extensions are never dropped: they outlive one schema. Before Atlas replays the history, database creates on the dev database every sequence and extension the history or the target holds (`CREATE … IF NOT EXISTS`), so a default calling `nextval` and a column of an extension's type (`citext`, `vector`, PostGIS) load there. An extension enters the history through a migration of your own with `CREATE EXTENSION IF NOT EXISTS …`, and the dev server must be able to install it (the stock `docker://postgres` image has `citext`, not `vector`). On a persistent `devUrl`, these sequences and extensions stay after the run; Atlas wipes only the schema it diffs.

An enum value Atlas adds goes into a file of its own a version earlier, since Postgres refuses to use a value added in the same transaction (55P04). Atlas cannot drop an enum value; database says how to write that migration by hand. A statement Postgres runs only outside a transaction needs its own file whose header holds `-- atlas:txmode none`. Atlas reads a file's header as the comment lines it starts with, other comments and `-- database:allow-unsafe:` among them, closed by a blank line (spaces or CRLF allowed); without that blank line it reads no directive and runs the file in one transaction, where the statement fails. database reads the header by the same rule, held to the pinned Atlas. On every dialect, `check` and `apply` refuse a file whose opening comments hold an `atlas:` line with no blank line after them, naming the file and the line: add the blank line, or remove the line. A first-line `-- atlas:delimiter` is the one exception, as Atlas reads it where it stands. database also refuses at check a header whose txmode Atlas refuses, quoting Atlas: a value other than `none` or `file` (`NONE` among them), `all`, or two txmode lines. `check` reads which from the parse tree and refuses one anywhere else, naming it: every `CONCURRENTLY` index build, drop or reindex and partition detach, `VACUUM` (not `ANALYZE` alone), a bare `CLUSTER`, a `CLUSTER`, `REINDEX TABLE` or `REINDEX INDEX` of a partitioned table or index, `REINDEX SCHEMA`, `DATABASE` or `SYSTEM`, `ALTER SYSTEM`, `CREATE` and `DROP DATABASE`, `ALTER DATABASE … SET TABLESPACE`, `CREATE` and `DROP TABLESPACE`, `DISCARD ALL`, `COMMIT` and `ROLLBACK PREPARED`, `CREATE SUBSCRIPTION` that makes a slot (its default), `DROP SUBSCRIPTION`, `ALTER SUBSCRIPTION … REFRESH` or a publication change that refreshes, and `ALTER SUBSCRIPTION … SET (failover)`. On a partitioned table Postgres refuses `CREATE INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY` of its index and `ADD … USING INDEX` in any file, so `check` refuses each, quoting Postgres, with the route that works: an index or a primary key or unique constraint added to `ONLY` the table, which builds nothing, then each partition's built concurrently (a key's added `USING INDEX` on the partition) and attached to it. A file Atlas runs in one transaction holds no `BEGIN`, `START TRANSACTION`, `COMMIT`, `END`, `ROLLBACK`, `ABORT` or `PREPARE TRANSACTION` of its own: its `COMMIT` would end Atlas's transaction, so what ran before a later failure would stay while the file is reported rolled back. `check` and `apply` refuse one from the file alone, before `check` replays anything, with no `-- database:allow-unsafe:` override; a `-- atlas:txmode none` file keeps its own, and a `SAVEPOINT` nests in Atlas's transaction. Every file database writes keeps Atlas's directives first that way.

`apply` works on a private copy of the migrations directory, checked against `atlas.sum`, so what Atlas runs is exactly what database read. Postgres orders the files by name alone, as SQLite does, and has Atlas run them in that order (`--exec-order non-linear`), whatever the lengths of their versions. It asks Atlas for its status and stops at any error, and at a file never applied whose name sorts before an applied one's, which Atlas would skip without a word: rename it to sort after the applied files. A file Atlas ran halfway outside a transaction resumes only if unchanged, since Atlas resumes it by statement count, and only while its version, compared as text, is the highest applied; so a `-- atlas:txmode none` file whose version sorts below that of a file applied or run before it is refused before anything runs, and one already halfway below another is refused with how to finish it by hand. A dry run comes next, so a database that has objects but no history is told to `baseline` before anyone is asked. Each pending file is then classified and approved as on SQLite (unsafe: a yes on a terminal or `-- database:allow-unsafe: <reason>`; cautious: `--yes` too), with lock warnings for statements that block a table: a non-concurrent index on an existing table (on a partitioned one with that route, and none for an index or key on `ONLY` it, which builds nothing), an added column whose default calls a function not known to be `IMMUTABLE` or `STABLE` (a listed built-in such as `now()`, or a history function whose every overload says so), a scanning constraint without `NOT VALID`, a `VALIDATE CONSTRAINT` after a statement of its file that took a lock blocking reads or writes (a `NOT VALID` ADD, an added column, an index build, a `LOCK` among them), which scans under that lock to the file's COMMIT (validate in a later file), a retype Postgres does not do in place (one without `USING` that keeps every value is safe and unwarned: its type unbounded or unchanged; a binary coercion to a type with no modifier, such as `varchar` to `text`, `cidr` to `inet` or `oid` to `regclass`; a longer `varchar` or `varbit`; more `numeric` precision at the same scale; a `timestamp`, `time` or `interval` of no less precision; an array of the same element; or a domain with no constraint over its type), and a retype in place that rebuilds the column's indexes, as one does that changes its collation, its operator family (`text` to `bpchar`) or an array column's declared type, an `ATTACH PARTITION`, which scans the partition unless the history proves its bound (a validated `CHECK` on the partition that holds the bound's own comparisons, with constants that read the same in every session, on a single-column `RANGE` or `LIST` key that is `NOT NULL` and has no `COLLATE` or operator class of its own, under a parent made without `LIKE` that has no index or foreign key and is no partition or child itself, with no `DO` block, `CALL` or call of a history function after the `CHECK`, any of which may drop it), and the parent's default partition, when it has one, either way, a `SET TABLESPACE`, `SET ACCESS METHOD`, `SET LOGGED` or `SET UNLOGGED`, which rewrites the table, materialized view or index it moves (none for a partitioned index, which holds no rows, and none for a move to where the relation already is: where the history left it, or, for one the applied history made without `USING` or `TABLESPACE`, or whose place a `DO` block, a `CALL` or a call of a function the history defined may have changed since, where the target's catalog says it is, which `check` and `apply` read when the `postgres` package is installed; without it, and for a relation a pending file makes, such a move warns), a `REFRESH MATERIALIZED VIEW` that is not concurrent, and a `LOCK` in `SHARE` mode or stronger. `apply` replays nothing, nor does `check` on a `docker://` `devUrl` or without the `postgres` package, so each warns from database's map of the file's text, which misses a lock a `DO` block, a function or `EXECUTE` takes, and a table a `DO` block renamed; `check`'s replay on a `postgres://` `devUrl` measures them, so run `check` on a `postgres://` `devUrl` before `apply`. Atlas then applies each file in its own transaction and records it, one Atlas call per file, so each file runs on a session of its own, as it would alone: a `SET` a file makes (`search_path`, `timezone`, `lock_timeout` and the like, or `set_config(…, false)`) ends with the file, and the next file does not see it. `check` replays each file on a session of its own, as apply runs it, and starts it as Atlas does: searching the schema and reading dates month first (`DateStyle` `ISO, MDY`), whatever devUrl's server defaults to, so a `RESET search_path` or `DISCARD ALL` returns to the schema there too. Between calls database reads the status and checks the history again; a failed file is named with its statement, and the files before it stay applied. Atlas holds a lock while it applies, so two applies never run at once. `--file` and `--local` do not apply to Postgres.

`baseline <db>` records every file of the directory as applied without running any, setting Atlas's history to the highest version among them (Atlas records each file by name until one whose version, compared as text, sorts above the one it is given), and refuses a database that already records migrations, and one whose tables are not the ones the history leaves on the dev database: on a `postgres://` `devUrl` Atlas compares the target's tables with the database that database's replay below leaves, before database drops it, and runs no file itself, and on a `docker://` one Atlas replays the files in its own container. Atlas OSS leaves out functions, procedures, triggers, views, materialized views, sequences, policies, domains, composite and range types, collations, rules, row level security, extensions, aggregates, `SECURITY DEFINER`, operators, casts, views' options (`security_invoker`, `security_barrier`, `check_option`), materialized views' indexes, a table's replica identity, event triggers and publications, and finds a database that differs only there in sync, so baseline compares them itself, through `postgres` (an optional peer, which baseline refuses without): it replays the history on the dev database's server as `check` does, database's objects and all, file by file in a database of its own, leaving out what reaches past it, and reads the target schema's catalog there and on the target with one query, so Postgres itself decides what a cascade, a rename or a move leaves. A statement the dev database refuses stops it too, naming the file, the statement and the error. The role the dev URL connects as stands for the target's, so a policy `TO CURRENT_USER` compares as each database was built. This needs a dev database that database can connect to: a `docker://` devUrl is Atlas's own container, so database baselines through Atlas alone only a history whose every statement is one it has proved makes none of these objects (a table, an index, a column or constraint change, an enum, a schema, data, a session setting, a comment, a grant, a rename, a drop), and refuses any other naming devUrl, whatever it makes. Each is compared by name, and some by their settings too: a trigger by when it fires, a policy by its command, roles and kind (permissive or restrictive), a sequence by its start, increment, bounds and cycle, a table's row level security by whether it is enabled and forced. One the database or the history lacks refuses the baseline, extensions' own objects aside (and a range type's constructors, which are the type's), as is a sequence a column owns (a serial's, an identity's, or one `OWNED BY` a column), which is its table's; a partition's copy of its parent's trigger is Postgres's own. An extension, an event trigger or a publication refuses only when the database lacks one the history creates, since a platform installs its own. Not compared, which baseline names on every run: views' and policies' queries and checks, triggers' `WHEN` clauses, view columns' defaults, columns' statistics targets, statistics objects, text search configurations and dictionaries, foreign data wrappers, servers and user mappings, grants and comments. Whatever Atlas says on stderr as a `diff` or a `baseline` compare succeeds, database prints as `Warning: Atlas: …`, as Atlas OSS may say there that it left part of a schema out. `status <db>` lists applied and pending files, and refuses an applied file edited since, naming it, as `apply` does: Atlas never runs it again, so restore the file, or put the change in a new one. Atlas prints every statement it runs, so keep secrets out of data migrations; take a snapshot (a PITR point, a Neon branch) before an unsafe apply, and prefer expand-and-contract to renames and drops in one deploy.

## SQLite transforms

Atlas wraps SQLite table rebuilds in `PRAGMA foreign_keys = off;` … `PRAGMA foreign_keys = on;`. That pragma is a no-op inside a transaction, which is exactly where D1 runs it — so the rebuild proceeds with FK enforcement still live and fails. `applySqliteMigrationTransforms()` rewrites the pair into a single `PRAGMA defer_foreign_keys = on;` prelude, which defers the checks to commit time. It is idempotent and leaves every `CREATE`, `ALTER`, and `INDEX` statement byte-identical.

The pragma defers checks, never `ON DELETE` actions. With foreign keys on (always on D1, and by default in `@libsql/client`), Atlas's `DROP TABLE t` first deletes every row of `t`: `CASCADE` and `SET NULL` change the tables that reference it, `RESTRICT` fails, and `NO ACTION` fails at commit, since the rows return under the renamed copy. So `database migrate diff` guards each rebuild of a referenced table. Between Atlas's copy and its drop it saves every table with a foreign-key path to `t` (Atlas's `new_t` too when it references `t`) into a `_database_keep_<table>` table, saves `t`'s `sqlite_sequence` value, and empties those tables, each after the tables that reference it. After the rename it refills them in the opposite order, restores the sequence, and drops the keep tables. Rowids survive every rebuild, the rebuilt table's included: a table keyed by an `INTEGER PRIMARY KEY` keeps them with its key, and any other rowid table carries them apart, in its keep table or, for `t` itself, in Atlas's copy, which database writes as `INSERT INTO new_t (rowid, …) SELECT rowid, …`. D1 caps a `SELECT` at 100 result columns, so a table with 100 stored columns and no `INTEGER PRIMARY KEY` keeps its rows whole under new rowids, and the classification names it (`t gets new rowids (100 columns, no INTEGER PRIMARY KEY)`). The guard doubles the writes to those tables, which counts against D1's 30-second limit per query on a large table; a 1M-row closure takes under a second on local SQLite. The diff refuses, naming the object, when a table it would empty has a trigger other than an FTS one (the trigger would fire on both the emptying and the refill), when a table already uses the `_database_keep_` prefix, or when the history does not show a reached table's columns. Before such a file applies, `check` and `apply` also read the database's own foreign keys and triggers, and refuse when a table no migration made references the rebuilt table (its rows would go with the drop) or a trigger no migration made sits on a table the guard empties.
