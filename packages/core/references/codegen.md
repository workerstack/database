# Codegen

## Config

```ts
/* database.config.ts */
import { defineCodegenConfig } from "@workerstack/database/codegen"

export default defineCodegenConfig({
	databases: {
		core: {
			dialect: "sqlite", // "sqlite" | "postgres"
			driver: "d1", // bun-sqlite | d1 | libsql | turso (sqlite) · neon (postgres)
			tables: "./src/db/core.tables.ts",
			filePrefix: "db.core", // generated file name prefix
			generators: ["dtos", "orm"], // omit to run all
			output: { default: "./src/db/_gen" }, // per generator too: { dtos: "./src/dtos" }
			fts: {
				post_translation: { columns: ["title", "body"], tokenizer: "porter unicode61" },
			},
		},
	},
})
```

A Postgres database lists its partitioned tables under `partitions`, each keyed as its constraint map keys it (`audit`, or `app.audit` for a `pgSchema` table) to its partitions' names, which live in its schema: `partitions: { audit: ["audit_2026", "audit_2027"] }`. Codegen refuses a key that is no table, a partition that is a table or is listed twice, and any on SQLite. A partition not yet listed fails closed: its violations name no column until codegen lists it.

`defineCodegenConfig` types the file, so a mistyped generator, `output` key or driver fails to compile, and database holds the file to a strict schema as it loads it, so a key it does not know, which a config built through a helper of your own passes the compiler with, is refused by name, with the file and where (`database.config.ts is not a valid database config: ✖ Unrecognized key: "filePrefx"`), never run on its default. `output.default` is the directory every generator writes to unless the config names its own output; without it, files go beside the tables file.

Under `isolatedDeclarations`, the constraints, entities, enum-checks, error-keys, field-names, rows, rqb-cols, sql-cols and table-names files compile; the DTO files and `_shared`, `relations.gen.ts` and `orm.gen.ts` infer their zod and drizzle types, as your tables module does, so keep them in a tsconfig without the flag (meta-contract §10).

A run writes nothing until every database's generators succeed, then writes them all at once, so a failing database leaves the others' files and `package.json` as they were. It then deletes what each database's last run wrote and no database wrote this time, but only files carrying database's own header (`@generated by database`, or a JSON `_generated` value starting `database `); another tool's generated file is refused like a file of your own. A table that was removed, a `filePrefix` that changed and an `output.default` that moved all count, and a run of the whole config (no database named, no `-g`) also deletes the files of a database the config no longer declares. Two databases that would write one path fail the run, naming both. In `package.json`, codegen owns `./tables`, `./relations`, `./entities`, `./field-names`, `./table-names`, `./rqb-cols/<table>`, `./sql-cols/<table>` and the `./dtos/*` subpaths that point at its own generated files, `<table>` being the table's kebab-case export name (`blog-posts`); your own `./dtos/*` entries stay. A package that exports two databases takes each one's subpaths under its name (`./core/dtos/post`). The record of what each database wrote is `.database.codegen.gen.json` beside `database.config.ts`, named under the `.gen.` convention formatters ignore (beside the tables file in `--tables` mode); commit it with the output. A database's name becomes the stem of generated identifiers, camel-cased across any character an identifier cannot hold (`my-db` gives `createMyDbDb` and `MY_DB_DB_CONSTRAINT_MAP`); a name that still makes no identifier fails the run. Without a `dialect` in the config, the drizzle builder each table's file imports decides it (`pgTable` or `sqliteTable`, through any re-export), and a database holding both is refused, as is a config `dialect` its tables contradict.

## Generators

`@workerstack/database/codegen/generators` exports each one directly; the CLI runs them by name via `-g`.

| Generator      | Output                                                                    |
| -------------- | ------------------------------------------------------------------------- |
| `columns`      | column selections and table names, so query code never hard-codes strings |
| `constraints`  | the `ConstraintMap` for the error handlers                                |
| `diagrams`     | ChartDB DDL, relations JSON and a summary for AI context                  |
| `dtos`         | Zod schemas and TypeScript DTOs for create, update, and read              |
| `entities`     | `generateId()` helpers bound to each table's id prefix                    |
| `enum-checks`  | SQL CHECK constraints for `c.enum()` columns                              |
| `field-names`  | a label for each field name, and their union type                         |
| `fts`          | the FTS5 metadata map, and its virtual tables, triggers and backfill SQL  |
| `manifest`     | the model as JSON, for consumers that are not TypeScript                  |
| `orm`          | a typed `createXDb(handle)` client wired to the driver                    |
| `relations`    | Drizzle v1 `defineRelations()` from the foreign keys                      |
| `rows`         | row types inferred from the tables                                        |
| `translations` | the constraint map's error keys and their en-US messages                  |

Every generated file opens with a checksum header:

```ts
/* @generated by database — do not edit. checksum: bb552c750aeb */
```

Writes are atomic (temp file plus rename) and skipped when the checksum is unchanged, so codegen is safe to run on every build and produces no spurious diffs.

A generated file's relative imports follow the tsconfig nearest the tables file: under `node16` or `nodenext` each names its extension, `.js` for a TypeScript file, or the `.ts` itself under `allowImportingTsExtensions` or `rewriteRelativeImportExtensions`; under `bundler` and the older resolutions, none, as before.

A plain drizzle column, built with no `c` helper, is typed by its data type. On Postgres its create and update DTOs take what Postgres takes for that type, so a value the database would refuse is a 400 from the DTO, not a 22P02 from the insert: a `uuid` is `z.guid()`; a `date` an ISO date, as `z.iso.date()` takes one, from year 0001, as Postgres holds one; a `timestamp` a local date-time and a `timestamptz` one with its offset, so neither loses the instant; a `time` an ISO time, as `z.iso.time()` takes one, and a `timetz` the same with its offset, its precision included (`time(3) with time zone`); an offset written as RFC 3339 writes one, `Z` or `±hh:mm`, as JSON Schema's `time` and `date-time` formats name it, at most 15:59 either way, as Postgres holds one; a precision on a time, a timestamp or an interval no longer fraction of a second, which Postgres would round (`timestamp(0)` rounds `23:59:59.6` into the next day), and one declared with no precision at most 6 digits, Postgres's default, which rounds a 7th (`23:59:59.9999995` into a plain `time` is `24:00:00`); an `interval` an ISO 8601 duration, each part at most the digits whose every value Postgres holds (a sum of parts past its range is the handler's 400), with no part below its fields' last (`PT1H` into an `interval day`, which Postgres stores as 0, is refused); a `numeric(p, s)` decimal digits within its precision and scale, a scale past the precision a fraction alone and a scale below 0 a whole number ending in that many zeros, nothing Postgres would round, and in number mode a number Postgres's rounding keeps within them; a string-mode `bigint` digits within int8; a `real` a number float4 holds and does not round to zero; an `inet` an address, its netmask optional; a `cidr` the same with no bit set past its prefix length, through `isCidr` from the package root; a `macaddr` or `macaddr8` any spelling Postgres takes with no blank in it and nothing after its last octet; a `bit(n)` exactly n bits. A few spellings Postgres also takes are refused for the canonical one (a date's `tomorrow`, `24:00:00`, a numeric exponent, a non-ISO interval, since 0.15 a uuid in braces or as bare digits, and since 0.21 an IPv6 address with a colon before its prefix or an empty part in its IPv4 tail, and an interval part of more digits than that, such as `PT2562047788H`; the 0.14, 0.15 and 0.21 changelogs list each). On SQLite a `numeric` takes decimal digits as Postgres's plain `numeric` does, a whole number of at most 15 and a fraction of at most 13, the digits SQLite's NUMERIC affinity reads back as sent: SQLite stores a text that reads as a number as an INTEGER or a REAL, and drizzle reads it back as text, which SQLite 3.53 writes for a REAL of 14 or 15 digits as another decimal (`57.2505567882849` as `57.250556788284897`), so a longer value, an exponent, a `+` or blanks came back as another number or spelling. Store a longer fraction as text, or in whole units. A taken value reads back in SQLite's spelling, `1.50` as `1.5` and `0.000000123` as `1.23e-07`. A read DTO keeps the plain type, as a read never refuses a stored row, with one exception: a float column reads back `Infinity` and `-Infinity`, which JSON writes as `null`, and the `null` D1 hands an infinity back as, and its published JSON Schema takes that `null` (`anyOf: [{ type: number }, { type: null }]`, typed `number | null`), but on Postgres a stored `NaN` fails the read DTO, since JSON Schema cannot represent it (SQLite stores a NaN as NULL). A data type database has no rule for (a `sparsevec`, a buffer, a date mode) fails codegen, naming the column and the types database does type.

## Analyzer

```ts
import { analyze, validateTables } from "@workerstack/database/codegen"

const result = await analyze("./src/db/core.tables.ts")
const { errors, warnings } = validateTables(result)
```

`analyze()` returns a promise of an `AnalysisResult` — `TableMeta` per table with `FieldMeta`, `FieldConstraintsMeta`, `ForeignKeyRef`, `UniqueIndexMeta`, `CheckConstraintMeta`, and `TimestampsMeta`. It loads the tables module and reads every table it exports as drizzle built it (`getTableConfig`) and as the `c` helpers recorded it, so a bound, an enum list or an id prefix is the value the module computes, however its source spells it. The module runs in a child process on the runtime codegen runs on, with only `PATH`, `HOME` and `NODE_OPTIONS` in its environment, database's own working directory (where the config is, or where you run it with `--tables`; `analyze()` takes `{ cwd }`), as the app and drizzle-kit run it, and 60 seconds to load, so a tables module must be import-safe, as drizzle-kit already needs it to be: no connection, no secret read, no work at import. Under node the child loads TypeScript itself, resolving imports as the nearest `tsconfig.json` does (`paths` included); bun does that natively. A module that fails to load, a column database cannot type, a `c.json` schema no module exports, or a key into a table the tables file does not export fails codegen, naming the file, the table and the column.

`validateTables()` checks an analysis before the generators run: names and id prefixes two tables may not share, one tenant column per table, state machines against their values, and primary keys a cursor can page.
